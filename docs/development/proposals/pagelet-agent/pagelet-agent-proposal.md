# Pagelet Agent 化提案

Document status: Draft (方向已验证)
Updated: 2026-07-30
Work item: TBD

> Pagelet 从编排式管道（single-shot LLM）演进为 Agent 模式的设计提案。
> 核心动机：让 AI 深度参与发现过程，解决当前洞察"太浅"和"无价值"的问题。

---

## 1 · 问题陈述

### 1.1 观察到的现象

当前 Pagelet 产出的洞察存在两个问题：
- **A. 发现太浅**——只是表层关联（"都提到了 X"），没有深层洞察（"X 在这里的用法和那里矛盾"）
- **C. 有发现但无价值**——技术上正确但用户看了觉得"so what"，不会改变行为

### 1.2 根因分析

AI 参与率不高：

```
代码决定看什么 → 代码组装上下文 → AI 分析一次 → 代码解析输出
      ↑                ↑              ↑
   AI 不参与        AI 不参与       唯一参与点
```

- AI 只在"分析"这一步参与，且是 single-shot
- 拿到的是每篇笔记 ~1800 字符的截断片段
- 无法根据发现追查更多信息
- 无法验证自己的发现是否真实

具体导致：
- **A（太浅）** 的原因：发现"矛盾"需要理解每篇笔记的论证逻辑再比较，在截断内容+单次推理中做不到
- **C（无价值）** 的原因：AI 不知道关联是否已被用户知晓（已有 backlink？），没有新颖性检查

### 1.3 产品战略判断

**修补思路的问题**：

```
发现太浅 → 加"追读"能力 → 可能好一些
发现无价值 → 加"新颖性检查" → 可能好一些
  → 但下次又发现新问题（不够 actionable / 角度单一 / ...）
  → 再加能力 → 永远在追赶
```

**Agent 化的思路**：

```
让 AI 自己决定怎么做（查找、分析、推理、验证、形成建议）
  → 模型能力提升 → 产品自动变好
  → 新场景 → 模型自己适应
  → 天花板跟着模型走，不跟着代码走
```

**本质区别**：修补是你在帮 AI 想"应该怎么分析"，Agent 化是 AI 自己想"应该怎么分析"。前者天花板是开发者的预想力，后者天花板是模型的推理力。

**决定**：赌模型能力，把控制权交给 AI。架构应该让模型能力成为产品杠杆。

## 2 · 方向验证实验

### 2.1 实验设计

日期：2026-07-30

**方法**：以 vault 中一篇 permanent 笔记（`4.permanent/permanent-AI/MCP.md`）为锚点，给 AI 完整的 vault 读取工具和自由探索空间，不限制搜索路径和轮次，看能否产出比 single-shot 显著更深的洞察。

**对照**：当前 Pagelet single-shot 对同一篇笔记的分析能力（表层关联、截断内容）。

### 2.2 探索过程

Agent 自主探索了 vault 中 14 篇笔记，跨越多个目录：
- `4.permanent/permanent-AI/` — 同领域 permanent 笔记
- `3.literature/literature-AI/` — 相关 literature 笔记
- `0.unsorted/` — 最新的未分类研究
- `c.freelancer/` — 实际项目的实现代码

探索策略：从锚点笔记提取线索（MCP 安全性、工具选择机制、标准化战略）→ 搜索相关笔记 → 深入阅读 → 比较推理 → 形成发现。

### 2.3 发现结果

产出 6 条跨笔记洞察，按类型分：

#### 发现 1：MCP 与 Agent 安全的未调和矛盾（类型：矛盾）

MCP 笔记赞美"基于 prompt 的工具选择"是优势（通用性）。Agent 安全笔记精确指出这个机制是 FuncPoison 攻击的根源。MCP 笔记的"数据安全"声明（"敏感数据留在自己的环境中"）给了虚假安全感——真正的威胁不是数据离开你的环境，而是你的环境通过合法持有的凭证执行违背意图的操作。

**为什么 single-shot 做不到**：需要理解两篇笔记各自的论证逻辑（一篇在说"这是优势"，另一篇在说"这正是漏洞"），不是关键词重合。

#### 发现 2：真实实现远超协议模型（类型：缺口）

opencode 的 MCP 实现包含 OAuth 2.0 + PKCE、动态客户端注册、权限层、doom-loop 检测。MCP 笔记把协议当完整方案（"万能转接头"），但实际只是传输/发现层，需要大量额外基础设施。

**为什么 single-shot 做不到**：需要读 `c.freelancer/` 下的实现代码笔记，和 `4.permanent/` 下的概念笔记做对比。

#### 发现 3：时间线揭示思维演进（类型：跨时间）

- 2025-03: MCP 笔记——乐观推广语气（"万能转接头"、"连接革命"）
- 2026-04: Agent 安全笔记——深度对抗性思维

用户的认知从"工具是好东西"演进到"工具是攻击面"，但 permanent 笔记还停在旧认知上。

**用户反馈**："这个是我自己没有意识到的认识和思路的演进"——验证了 Agent 能帮用户看到自己的盲区。

#### 发现 4：标准化无护城河（类型：矛盾）

"AI 没有护城河" memo 论证开放标准消解竞争优势。MCP 笔记描述 Anthropic 的"开放+控制"策略。两者合起来说明：MCP 本身会变成基础设施而非差异化来源。

#### 发现 5：Cline Memory Bank = 记忆投毒攻击面（类型：正反面）

Cline 笔记热情描述的 persistent memory 模式，正是 Agent 安全笔记中 MemoryGraft 攻击的具体实例。两篇笔记从正反面描述同一机制，从未被连接。

#### 发现 6：高质量笔记卡在管道中（类型：结构）

三篇 Agent 安全笔记是 vault 中最有深度的技术写作，但停在 `0.unsorted`，未进入 permanent 管道。

### 2.4 实验结论

| 验证维度 | 结果 |
|---------|------|
| 多轮检索是否找到了 single-shot 遗漏的东西？ | **是** — 6 条发现中至少 4 条需要读多篇完整内容后比较推理 |
| 洞察是否足够深？ | **是** — 指出了具体矛盾、时间演进、未连接的正反面 |
| 是否可行动？ | **是** — 每条都有"你应该做什么" |
| 用户主观评价 | **有价值** — 特别是"思维演进"类发现，用户自己没意识到 |

**核心结论**：在用户的真实 vault 上，给模型自由探索空间 + 工具确实能产出 single-shot 不可能达到的深度。

**假设验证**："AI 参与率不高是洞察浅的根因"——**成立**。提高 AI 参与率（多轮检索、完整内容阅读、自主追线索）直接产出了更深的洞察。

## 3 · Pagelet Agent 定义

### 3.1 身份

Pagelet Agent 是一个默默阅读 vault 的研究助手。它不等用户提问，而是在用户写完/回看笔记时，主动告诉用户"有一件事你可能没注意到"。

### 3.2 目标

找到**用户仅凭当前视野看不到的、但知道了会改变行为的东西**。

具体产出类型（从实验中验证）：

| 类型 | 示例 | 实验验证 |
|------|------|---------|
| 矛盾 | "MCP 的优势正是安全笔记中指出的漏洞根源" | 发现 1、4 |
| 遗忘/演进 | "你对工具安全的认知在 13 个月里发生了根本转变" | 发现 3 |
| 缺口 | "MCP 笔记的架构模型缺少实际生产需要的层" | 发现 2 |
| 正反面 | "Cline 的 memory 模式 = 安全笔记中的攻击面" | 发现 5 |
| 结构 | "高质量笔记卡在管道中未被推进" | 发现 6 |

**共性**：都是需要读多篇笔记完整内容 + 推理才能得出的。

### 3.3 输出标准

- 产出必须指向**具体的源笔记 + 具体位置**
- 用户知道这件事后，**会做一个动作**
- 上限由**信噪比**定：1 条高置信发现 > 5 条"可能相关"
- "没有值得说的"是合法结论

### 3.4 和 Chat Agent 的边界

| | Chat Agent | Pagelet Agent |
|---|---|---|
| 触发 | 用户提问 | 系统事件（编辑结束） |
| 目标 | 回答问题 | 主动发现 |
| 输出对象 | 用户当前问题 | 当前笔记的盲区 |
| 何时该沉默 | 不该（用户在等答案） | 经常（没发现就别说） |

## 4 · 触发机制

### 4.1 设计原则

触发点是"用户可能要消费结果的时刻"，不是"内容变了的时刻"。
编辑中不跑，编辑结束后跑。

### 4.2 触发信号

- **离开笔记时**——用户写完切走了，对这篇笔记跑 Agent
- **打开笔记时（内容自上次分析后有变化）**——上次没来得及跑，此刻补上
- **空闲 N 秒后**——用户停止编辑一段时间

### 4.3 防重复

- Content hash 比对，无变化不重复跑
- 结果缓存，下次打开直接展示

## 5 · 结束边界

### 5.1 Lead-Driven 停止逻辑

```
读当前笔记
  → 提取线索(leads)
  → 线索为空 → 结束
  → 有线索 → 逐条追查
    → 发现高置信 insight → 输出，结束
    → 所有线索追完无 insight → 静默结束
    → 派生新线索 → 继续追
    → 触发熔断器 → 输出已有最高置信发现，强制结束
```

### 5.2 熔断器（防御性）

| 约束 | 值 | 目的 |
|------|---|------|
| 最大工具调用 | 30 | 防止无限循环 |
| 最大墙钟时间 | 180s | 后台不阻塞 |

### 5.3 成本控制

靠触发频率而非单次限制：content hash 去重 + debounce + 每日上限。

## 6 · 结果展示

### 6.1 时态模型

不分层，分时态：
- Agent 已跑过 → 展示缓存结果
- Agent 未跑过 → 加载态，后台跑完推送

### 6.2 统一 Insight Card

所有发现以一致的方式呈现：

```
┌─────────────────────────────────┐
│ [类型: 矛盾/演进/缺口/正反面]     │
│                                 │
│ 主文本（发现描述）                │
│                                 │
│ 来源: note-a.md, note-b.md     │
│                                 │
│ [查看] [稍后]                    │
└─────────────────────────────────┘
```

## 7 · 实现关键决策

### 7.1 已确认的实现选择

| 决策 | 结论 | 理由 |
|------|------|------|
| Agent loop 机制 | 复用 PaAgentLoop，注入 Pagelet mode config（LeadDrivenPolicy + 读工具子集 + 输出到 insight cache） | 避免重复建设，loop 机制通用 |
| 模型选择 | 和 Chat Agent 用同一个模型 | 最简单，能力一致 |
| 读工具子集 | search_memory, get_current_note_context(anchor-bound), search_vault_snippets, inspect_obsidian_note, search_vault_metadata, list_recent_notes, read_note_outline + webSearch | 覆盖发现所需的所有检索维度 |
| Token 预算 | 不设 per-run 限制，后续优化 | 先验证价值，再优化成本 |
| 每日调用上限 | 36 次/天 | 平衡覆盖率和成本 |
| 迁移策略 | 直接替换——Agent 上线后关掉所有 single-shot 管道 | 不维护两套并行系统 |
| UI 渲染位置 | 复用现有 Bubble → Panel 渐进展开，Agent insight 作为 DeliveryCandidate 进入 Attention-Aware Delivery 管道 | 不新建 UI 组件 |

### 7.2 技术问题（SDD 必须解决）

| ID | 问题 | 描述 | 要求 |
|----|------|------|------|
| T1 | 锚点冻结 | 用户切走后工具可能读到新笔记 | 冻结 anchor path + content + mtime；使用 path-bound 工具变体，不复用 Chat 的 active-file 工具 |
| T2 | Cache 失效 | 仅 contentHash 不够 | 缓存身份含：anchor snapshot + source snapshots + Data Boundary identity + pipeline/schema version |
| T3 | 质量门 | 自报 confidence 不可靠 | source 验证（来源笔记真实存在 + snippet 支撑 finding）+ novelty check（和现有 backlinks/已展示 insights 对比）|
| T4 | 并发调度 | Chat 和 Pagelet 争 LLM API | Chat 优先；Pagelet 当前 turn 完成后暂停让出；简单信号量实现 |
| T5 | 成本控制 | 后台自动任务成本不可控 | 36 次/天上限 + 熔断器 30 calls/180s + Settings 展示消耗量 |
| T6 | B-121 集成 | Agent 产出如何进入 Delivery 管道 | Agent insight 转为 DeliveryCandidate 对象，参与 Attention-Aware Delivery 的指纹/seen/nudge 流程 |
| T7 | 现有管道迁移 | Agent 上线后 single-shot 怎么办 | 直接替换：移除 preload/discovery/review/recap/quiet-recall 的 single-shot 调用路径 |

## 8 · 设计决策记录

| # | 决策 | 理由 |
|---|------|------|
| D1 | Agent 化方向而非修补管道 | 天花板跟模型走而非跟代码走；实验验证有效 |
| D2 | 实验验证通过 | 6 条深层洞察，用户确认有价值 |
| D3 | 复用 Chat Agent 工具链（读子集 + webSearch） | 避免能力重复建设 |
| D4 | 不分层，分时态 | 避免 UI 切换割裂 |
| D5 | 触发点为"编辑结束" | 避免频繁触发浪费 |
| D6 | Lead-driven 停止逻辑 | 深度由笔记复杂度决定 |
| D7 | 熔断器宽松（30 calls / 180s） | 防异常，不限正常探索 |
| D8 | "无发现"是合法结论 | 信噪比优先 |
| D9 | webSearch 作为验证工具 | 发现靠 vault，验证可借外部 |
| D10 | UI 收敛到统一 Insight Card | 底层统一后分场景 UI 无意义 |
