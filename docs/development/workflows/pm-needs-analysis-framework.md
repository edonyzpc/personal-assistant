# PM Needs Analysis Framework

产品需求分析引导框架。当收到用户需求/功能请求时，按此流程逐层分析，
避免直接跳到"做不做"的结论。

## 使用方式

- Claude/Codex 在收到用户需求讨论时，按本文档的层次顺序引导用户思考
- 每一层提供结构化问题清单，辅助用户填充判断
- 不替用户做决策，而是确保每个判断维度都被覆盖
- 可以在任意一层停下来深入讨论，不要求一次走完

---

## Phase 1: 还原用户与场景

> 目标：搞清楚"谁在什么情况下遇到什么困难"，不急着判断。

### 1.1 用户画像

| 维度 | 追问 |
|------|------|
| 身份 | 提出需求的人是什么角色？（终端用户/创作者/开发者/运营） |
| 频率 | 这个场景多久发生一次？（日/周/月/偶发） |
| 技术能力 | 用户能否自己用替代方案解决？ |
| 为什么找我们 | 用户为什么向本产品提这个需求，而不是用别的工具？ |
| 代表性 | 这是个人偏好还是一类用户的共性需求？ |

### 1.2 场景还原

按时间线还原用户的完整行为链：

```
触发事件 → 用户意图 → 当前行为 → 遇到的摩擦 → 期望的结果
```

要求：
- 写出至少 2-3 个具体场景（不要抽象描述）
- 场景要具体到可以"演"出来的程度
- 注意区分"高频低摩擦"和"低频高摩擦"场景

### 1.3 关键追问清单

在分析前，理想情况下应该向用户确认：

- [ ] 你上一次遇到这个问题是什么时候？具体发生了什么？
- [ ] 你现在是怎么解决的？（即使方案不完美）
- [ ] 如果有了这个功能，你想象的操作路径是什么？
- [ ] 这个需求对你来说是"必须有"还是"有了更好"？
- [ ] 你愿意为此付出什么代价？（学习成本/付费/数据权限）

## Phase 2: 拆解真实需求

> 目标：穿透表层请求，找到底层 Job to Be Done。

### 2.1 需求分层（连续问"为什么"）

```
表层需求（Feature Request）
  └─ 用户说的原话，具体的功能描述
       ↓ 为什么想要这个？
中层需求（Goal）
  └─ 用户想达成的目标
       ↓ 为什么这个目标重要？
深层需求（Job to Be Done）
  └─ 用户在生活/工作中要完成的根本任务
```

### 2.2 JTBD 标准表述

用这个句式提炼：

> **When** [触发场景]，
> **I want to** [期望的行为/能力]，
> **So that** [最终要达成的结果]。

### 2.3 需求类型判断（Kano 模型）

| 类型 | 定义 | 特征 |
|------|------|------|
| 基本型（Must-be） | 没有会不满，有了不惊喜 | 用户默认你应该有 |
| 期望型（One-dimensional） | 做得好就满意，做不好就不满 | 用户主动提出的通常在这层 |
| 兴奋型（Attractive） | 没有不会不满，有了会惊喜 | 用户自己都没想到的 |

关键判断：**用户提出的需求在哪一层？真正的差异化机会在哪一层？**

---

## Phase 3: 市场与替代方案

> 目标：了解用户今天怎么解决这个问题，以及市场上谁在解决。

### 3.1 现有替代方案地图

不只看"竞品"，而是看**用户实际采用的所有解决方式**：

| 替代方案 | 用户满意度 | 摩擦点 | 切换到我们的动力 |
|----------|-----------|--------|-----------------|
| 自己手动做 | ? | ? | ? |
| 不做/忍受 | ? | ? | ? |
| 通用工具（如 ChatGPT） | ? | ? | ? |
| 专用工具 | ? | ? | ? |
| 平台内置功能 | ? | ? | ? |

### 3.2 竞争空间判断

```
已被充分解决的（Red Ocean）：
  → 通用方案已经够好，用户满意度高

部分解决的（有缝隙）：
  → 现有方案有明确痛点，但没人专门解决

未被解决的（Blue Ocean）：
  → 需要独特能力/数据/场景才能解决
```

### 3.3 关键问题

- 用户在现有方案上的不满足感够强吗？
- 我们能否提供现有方案做不到的东西？
- 如果能，那个"做不到"是技术壁垒、数据壁垒、还是体验壁垒？

---

## Phase 4: 产品匹配度评估

> 目标：判断"我们该不该做"。

### 4.1 战略对齐检查

逐项回答（Yes/No + 理由）：

| 维度 | 问题 | Yes/No | 理由 |
|------|------|--------|------|
| 定位 | 这是我们产品核心要解决的问题吗？ | | |
| 差异化 | 我们有明确的差异化优势吗？ | | |
| 用户群 | 需要这功能的人是我们的目标用户吗？ | | |
| 资源 | 以当前团队规模，投入产出比合理吗？ | | |
| 协同 | 做了这个能强化/复用现有能力吗？ | | |
| 风险 | 做了会不会模糊产品定位？ | | |

### 4.2 能力-意愿矩阵

|  | **该做**（符合定位） | **不该做**（偏离定位） |
|--|---------------------|---------------------|
| **能做**（有技术/资源） | 立项，进入方案设计 | 明确拒绝，记录原因（避免反复讨论） |
| **不能做**（缺能力/资源） | 列入长期规划，关注能力建设时机 | 忽略 |

### 4.3 产品北极星校验（PA 专用）

对照 PA 的设计哲学逐条检查：

- [ ] 是否符合"随手记下，需要时自然浮现"？
- [ ] 是否"Less management, more capture"？
- [ ] 是否"Less generation, more return"？
- [ ] 是否"Less interruption, more right-time presence"？
- [ ] 是否"安静且可信"？

如果多项不符合，需要找到特殊理由才能继续。

## Phase 4.5: 粗略估算

> 目标：给决策提供资源维度的输入，不要求精确，只要量级对。

### T-shirt Sizing

| 尺寸 | 工作量 | 典型特征 |
|------|--------|----------|
| XS | < 1 天 | 配置/文案调整，无新代码 |
| S | 1-3 天 | 小功能，单模块内闭环 |
| M | 1-2 周 | 跨模块协调，需设计+开发+测试 |
| L | 3-4 周 | 新子系统，涉及架构决策 |
| XL | > 1 月 | 基础设施级变更，影响面广 |

### 估算要点

- 这个需求的最小可行方案大概在什么量级？
- 团队当前有余力吗？机会成本是什么？（做这个意味着不做什么）
- 是否有技术前置依赖需要先解决？

---

## Phase 5: 决策

> 目标：做出明确决策，并记录理由。

### 5.1 四种决策路径

| 决策 | 含义 | 适用条件 |
|------|------|----------|
| **Build** | 独立功能立项 | 高频 + 高价值 + 强匹配 + 有差异化 |
| **Leverage** | 借力现有能力顺带满足 | 需求合理，不值得独立投入，但现有架构可低成本支持 |
| **Redirect** | 引导用户用已有方案 | 已被充分解决，我们无附加价值 |
| **Decline** | 明确不做 | 偏离定位 / 模糊产品形象 / ROI 过低 |

### 5.2 决策前检查清单

- [ ] 频率够高吗？（影响多少用户、每人多频繁）
- [ ] 现有替代方案的摩擦够大吗？（值得用户换工具）
- [ ] 我们有独特优势吗？（别人做不到/做不好的）
- [ ] 做了对核心指标有贡献吗？（留存/活跃/付费）
- [ ] 不做会流失用户吗？
- [ ] 做了会模糊定位吗？

### 5.3 决策记录模板

```markdown
## 需求：[一句话描述]

**决策**：Build / Leverage / Redirect / Decline
**日期**：YYYY-MM-DD
**估算**：XS / S / M / L / XL
**利益相关方**：[谁参与了这个决策/谁需要知道结果]
**理由**：[2-3 句核心判断]

### 关键事实
- [支撑决策的关键信息 1]
- [支撑决策的关键信息 2]

### 如果未来需要重新评估
- 当 [条件 A] 发生时，重新考虑
- 当 [条件 B] 改变时，重新考虑
```

## Phase 6: 方案探索（仅当决策为 Build 或 Leverage 时）

> 目标：找到最小可行的切入点。

### 6.1 方案梯度

从小到大列出所有可能的方案：

| 级别 | 方案描述 | 成本 | 覆盖度 | 风险 |
|------|----------|------|--------|------|
| 最小 | 不写代码，用文档/workflow 引导 | 极低 | 低 | 无 |
| 轻量 | 借用现有能力，微调体验 | 低 | 中 | 低 |
| 中等 | 新增小模块，利用现有基础设施 | 中 | 中高 | 中 |
| 重量 | 独立功能模块设计开发 | 高 | 高 | 高 |

### 6.2 选择原则

- 优先选择能**验证假设**的最小方案
- 第一版的目标是**学到东西**，不是覆盖所有场景
- 问自己："如果这个方案上线后没人用，我们损失了什么？"

### 6.3 成功标准

上线前必须定义"怎么算成功"：

- **核心假设**：这个方案在验证什么假设？
- **成功信号**：什么现象出现说明假设成立？（用户行为/数据指标/定性反馈）
- **失败信号**：什么现象出现说明假设不成立？
- **观察周期**：给多长时间观察？（避免过早下结论或无限拖延）

## 使用示例

```
用户："我想要 PA 帮我根据照片生成社交媒体文案"

Phase 1 → 谁？什么频率？什么场景下发生？
Phase 2 → 真正的 Job 是"无摩擦分享生活"还是"写出爆款"？
Phase 3 → ChatGPT/小红书 AI 已经解决了吗？解决得好吗？
Phase 4 → PA 的"记忆+回忆"能比通用 AI 好在哪？符合北极星吗？
Phase 5 → Build / Leverage / Redirect / Decline？
Phase 6 → 如果是 Leverage，最小切入是什么？
```

---

## 注意事项

1. **尽量不跳层**：每一层的判断依赖前一层的输入，跳过会导致"凭直觉决策"。交互场景中允许用户主动跳层，但应提醒被跳过的维度并标注为"待补充"
2. **允许停在中间**：信息不够时停在某一层等待更多输入，好过强行结论
3. **区分"用户说的"和"用户需要的"**：用户的 feature request 是线索，不是规格书
4. **记录 context**：决策的质量取决于当时的 context，记下来便于未来复议
5. **定期回顾**：市场和产品能力都在变化，Decline 的决策可能因为新条件变成 Leverage
