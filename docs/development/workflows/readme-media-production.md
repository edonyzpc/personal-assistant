Owner 已选择“阅读积累 → 短文与分享成果”，要求突出 PA Agent、图片生成、Pagelet
主动洞察和 command；授权先修改双语正文，以占位表示素材，后续由 Owner 制作替换。
本指南描述要拍什么、怎样操作和放在哪里，不声称这些新场景已经拍摄成功。

## 先按这个顺序准备

1. 从[公开示例](../../guides/reading-to-sharing-demo.md#示例笔记)复制四篇笔记到独立的非敏感演示库；不要把本指南或项目治理文件一起导入。
2. 准备 Chat、Memory 检索与图片服务，先让前三篇素材笔记完成 Memory 准备。
3. 用第四篇写作提纲拍正常阅读、主动洞察和 Chat 交接，再依次完成写作、配图和分享；本轮未拍到提示时按下文备用剪辑继续。
4. 每个关键界面顺手截取原始 PNG；完成后补拍主图、成片开场和收尾。
5. 按本页的媒体 ID 替换两个 README 中对应占位。默认使用五处素材，其他截图保留备选。

示例笔记和提示词的唯一正文在公开示例中；本页的提问 A/B/C 链接直接跳到对应内容，
修改故事时先改示例，再核对本页镜头与两个 README，避免多份文本漂移。

## README 展示与版式

页面按“品牌/影响力/演示 → Chat 与 Memory → Pagelet → 写作、图片与分享 →
日常记录工具 → 快速开始 → FAQ/帮助 → 开发与贡献”展开。

- 品牌居中、正文左对齐；恢复版本、GitHub 发布资源下载量和 Stars。下载量不写成用户数。
- 主图让人看懂“旧笔记怎样帮助形成新作品”，默认兼作视频封面；需要时可从同一故事另选封面帧，README 不重复放两张近似画面。
- 每个重点能力一个收益标题、短说明和有效画面；详细操作由指南承接。
- 数据、费用和平台支持留在用户区；源码构建、协议、测试、架构和素材维护留在开发区。
- 主图同时呈现 PA 界面和成果，不能只裁出两句回答；也不要把整张高分辨率桌面缩到不可读。

主图可让成稿与可读的真实来源引用同屏，或用旧笔记与新作品的对照呈现联系；选择
最清楚的一种，不要求把所有来源、文章和配图塞满一屏。S4 承担详细的材料与来源
展示。静态主图即使不播放视频也应说明价值，不能只剩一张配图或泛化的 AI 回答。
本轮使用静态图和用户点击播放的视频，自动循环动图暂缓。

## 录制前的环境准备

| 检查 | 准备方式 |
| --- | --- |
| 构建一致 | 使用与要展示能力对应的当前构建；记录 PA 构建、Obsidian 版本、平台和界面语言。旧正式版可能没有同样入口。 |
| 数据范围 | 使用独立非敏感演示库，检查“PA 可以使用的笔记”和排除规则。新建文件夹本身不会限制后台处理范围。 |
| Chat 与 Memory | 配好聊天和笔记检索；前三篇素材笔记已准备。录制前完成一次普通 Chat，确认连接就绪，不提前手动发现主演示笔记。 |
| 图片 | 配置当前支持的 OpenAI 或 Wan 图片连接及账户权限，选择可用横向尺寸、一张结果。自定义聊天连接不代表支持生图。 |
| Pagelet | 开启拾页、“在后台发现笔记关联”“主动提示”，显示角色；避开静默时间、提示冷却和专注模式，检查自动发现用量。 |
| 画面 | 统一主题、字体和内容，关闭无关侧栏；保留笔记与 PA 面板的关系。不要出现凭据、私人笔记或无关账户信息。 |

这是完整演示的准备，不是普通用户开始 Chat 的最低条件。数据调用、模型费用和
能力边界见[手册](../../../Manual-CN.md)、[拾页指南](../../guides/pagelet-user-guide.md)
和[图文指南](../../guides/multimodal-chat-user-guide.md)。

## 主片 V1：约两分钟

主线：**阅读积累 → 主动洞察 → Agent 整理材料 → Writing 成文 → CreateImage 配图 → 保存与分享**。

以下是首轮粗剪的参考时长，合计约两分钟，不是实际执行耗时或硬性验收上限。
先录完整过程，再按“看清任务、理解结果、辨认来源”调整节奏。等待可以剪短或
加速并注明；拥挤时先减少重复展示，再增加关键操作和结果的停留，不用加速点击
压缩用户理解时间，也不要求按秒数完成真实任务。

| 镜头/粗剪参考时长 | 操作 | 画面必须呈现 | 建议字幕 |
| --- | --- | --- | --- |
| 01 / 约 5 秒 | 全部任务完成后补拍：只展示已保存的图文成稿，卡片留到结尾 | 文章、配图与旧笔记的联系，保留可辨认 PA 界面 | 从几篇旧笔记，到一篇新的作品 |
| 02 / 约 6 秒 | 打开《写作提纲：让阅读用起来》，补入示例中预留的最后一句，停留阅读 | 正在处理的写作问题、Obsidian 笔记和 PA 角色 | 我想把读过的东西用起来 |
| 03 / 约 10 秒 | 记录实际出现的拾页轻提示，按界面打开提示并选择“查看洞察” | 正常阅读到提示出现的过程，用户主动选择查看 | 阅读时，相关的旧想法回来了 |
| 04 / 约 15 秒 | 展开有效发现，打开一篇来源核对，回到发现，选择“在聊天中讨论” | 具体关联、来源和接续动作 | 看见关联，也能回到原文 |
| 05 / 约 20 秒 | 检查“来自 Pagelet”的材料，新 Chat 选择“我的笔记”，发送[提问 A](../../guides/reading-to-sharing-demo.md#提问-a) | Agent 使用旧材料形成有区别的整理；停留在关键判断及来源 | 让 PA 把积累整理成可用的素材 |
| 06 / 约 25 秒 | 输入 `@`，展示菜单并选 Writing，发送[提问 B](../../guides/reading-to-sharing-demo.md#提问-b)正文；打开文案版本，按下文步骤预览、确认并保存 | command 入口、文章关键段落、版本界面和明确保存动作 | 用 Writing，把材料写成文章 |
| 07 / 约 18 秒 | 同会话选择 CreateImage，发送[提问 C](../../guides/reading-to-sharing-demo.md#提问-c)正文 | 明确的生图请求、少量任务状态、真实图片及操作按钮 | 再为文章生成一张配图 |
| 08 / 约 12 秒 | 接上镜图片结果，点击“保存到笔记”，选择刚保存的文章，再打开文章 | 明确选择目标笔记，图片确实进入同一篇笔记 | 文字和图片，留在自己的笔记里 |
| 09 / 约 15 秒 | 选文章中的一段，命令面板运行“将所选内容分享为卡片”，展示预览与导出结果 | 选区到卡片的关系，结尾给成品足够停留 | 把值得留下的一段，分享出去 |

镜头 07–08 剪成连续动作段，但“生成”与“保存”仍清楚可辨。镜头 05、06、09
优先留出理解结果和确认保存的时间；提示词用简短意图字幕承接，全文由公开示例
提供。不要用机械的点击次数公式替代粗剪检查。

command 展示分两层：Chat 的 `@Writing` / `@CreateImage`，以及 Obsidian 命令面板的
“将所选内容分享为卡片”（English: Share Selection as Card）。截图只展示实际可用项，
不声称支持任意自定义命令、脚本执行或未经展示的外部发布。

### 主动洞察如何拍

从编辑写作提纲开始保留连续原片。当前调度会在编辑停顿、切换笔记等活动后按条件
尝试发现；发现质量、来源、额度、冷却及界面状态都可能影响提示。停留在提纲阅读，
不要为了催结果反复切换、重复付费请求或事先手动发现。

若出现的有效关联不是跑步记录，采用实际发现。跑步只提供生活类比，不证明学习
效果。没有提示时先检查上述条件；仍无新结果就保留缺口，不伪造提示或固定输出。
手动“拾页：发现关联”可另拍为手动入口，不能冒充自动过程。旧结果不会仅为录制重复提醒。

“在聊天中讨论”只准备新会话与材料，需要拍到用户检查后发送。打开面板也不等于
发起一次发现。画面字幕不要把这些动作写成全自动。

### 备用剪辑：本轮未拍到主动提示

拍摄前按可用时间和愿意消耗的 AI 额度设定本轮上限。核对环境准备中的提示条件后，
到达时间或额度上限就停止等待，切换备用版；不为拍到提示反复付费重试，也不以
固定拍摄天数保证成功。如需熟悉“查看洞察 → 核对来源 → 在聊天中讨论”，可先在
非主演示笔记上排练手动发现；排练也可能使用额度，正式录制前仍需重查用量和提示条件。

1. 保留镜头 01–02，略去未拍到的 03–04，直接接 05；过渡字幕用
   “直接提问，让旧笔记参与思考”，明确这是 Chat 中的检索。
2. 镜头 05 不展示不存在的“来自 Pagelet”材料，按[提问 A 的无交接分支](../../guides/reading-to-sharing-demo.md#提问-a)
   操作，再接写作、配图、保存和分享。按剩余真实画面重排时长，不强凑固定秒数。
3. S3 若另拍到手动发现，可使用其真实发现、来源和讨论入口，图注明确“手动运行”；
   没有有效结果则保留素材待补。手动发现不替代主动提示证据。
4. 替换时同步两份 README 的视频说明与 S3 图注，按实际展示命名；备用版注明
   “本片未包含主动提示实拍”。已取得的素材可先交付，主动提示缺口继续保留，
   不把备用版标成完整主线全部拍摄通过。日后取得真实主动过程，再补回 03–04。

### Agent 这一镜如何拍

提问 A 的重点是“过去的积累改变了今天的理解”：图表记录提供直接经历，阅读札记
保留适用条件，生活记录可能提供类比。选择真实有来源、可看出材料差异的回答。
不要求固定措辞，也不强求用完全部三篇。

核对本次是否实际检索了 Memory；只有普通笔记读取时就按真实行为标注。
活动提示可短暂出现，最终主画面以用户问题、整理结果和来源为主，不用调试日志代替价值。

### 写作、图片和分享的保存步骤

1. 文案完成后打开“文案版本”，展示正文及操作，再点“保存为笔记”。
2. 标题填写“收藏之后，先做一小步”；在“更改位置”填 `PA演示/成稿`。
3. 查看预览，明确确认后保存，点击“打开笔记”。默认版本图片随该次保存规则处理。
4. 回到同一 Chat 发起图片任务；生成完成后点击“保存到笔记”，选择
   `PA演示/成稿/收藏之后，先做一小步.md`。不要把生成完成剪成自动插入文章。
5. 回到成稿，选一段约 80–140 字、有独立意思的正文；用命令面板进入分享卡片。
6. 查看文字完整性与实际分页，按可用选项调整，保存或复制成品。

从 `@` 菜单选中任务后，只粘贴提示正文；也可直接粘贴带 `@Writing` 或
`@CreateImage` 的完整提示，二者不重复叠加。保留用户必要选择，不伪造省掉的确认。
分享卡片是内容排版，与 AI 生成配图分别命名。

## 可选补充片

### V2：继续编辑图片，约 15–25 秒

在已有图片上点击“编辑”，输入：

> 保留现有纸张质感、颜色和左右构图，把右侧的小柱状图改成一本打开的手写笔记，增加一支铅笔，减少散落便签。不要增加文字。

保留“点击编辑 → 修改要求 → 新旧结果”，体现原图仍然保留。如果最终采用新版，
选择该版本接入保存流程；未采用的版本不混作原始生成结果。

### V3：Agent 整理成稿属性，约 10–20 秒

先确认笔记操作能力可用，输入：

> 请把 PA演示/成稿/收藏之后，先做一小步.md 的 status 属性设为 draft，topic 属性设为阅读复用。保留其他属性和正文，只修改这一篇笔记。

保留“明确请求 → 实际执行结果 → 打开属性区”。以笔记的真实变化为准，不只拍一句
“已完成”。此操作仅限演示成稿，不修改原始材料。

## 拍摄与交付规格

- 桌面可从 1920×1080 或接近尺寸开始，横向 16:9/16:10 都可；适当放大界面文字。
  需要裁切特写时可提高采集分辨率，不要求为此更换设备。成片可用 30fps、H.264 MP4，
  默认以无声字幕讲清意图；体积按下文托管方式确定。
- 小菜单、保存按钮等不易辨认时，适度放大光标或插入局部特写，随后回到笔记与 PA
  的整体关系。导出后在 README 桌面默认宽度及窄屏预览；看不清时先调整字号、取景
  和停留，必要时补拍，不以采集分辨率或单一宽度判断通过。
- 静态界面优先原始 PNG；保留未加字幕的清晰录屏、生成配图和导出的卡片。裁切后
  仍应看得懂笔记与 PA 的关系；不绘制假 UI，不替换实际输出文字。
- 每个关键结果停留数秒。可以补录开场成果和收尾，剪掉等待需说明；不将剪辑后
  两分钟描述为完成整项任务的实际速度。可在片头或相应片段注明等待已剪短/加速，
  不因片段短就省略必要说明。
- 使用同一主题/字号/演示故事；中英文 README 可以共用界面素材，分别写图注。
- 交付时附：拍摄日期、PA 实际构建/源码身份、Obsidian 版本、平台、界面语言、
  对应镜头/截图 ID、等待加速或拼接说明。没有实际观察到的能力保留未验证。

## 媒体体积与视频托管

- 区分采集原件和发布副本：清晰 PNG、完整录屏等原件由制作者保存；
  `docs/assets/readme/` 只放选定并优化过的发布图片，不提交录屏原片或新成片。
- 静态发布图可从宽 1200–1600px、单张约 500KB 以内开始优化。这是参考目标，
  不是牺牲文字和来源可读性的硬上限；按实际画面选择 PNG、JPEG 或静态 WebP，
  并让文件名及 README 引用与最终格式一致。压缩后重新检查桌面和窄屏效果。
- 视频使用 GitHub `user-attachments` 或经授权的 Release 附件托管，README
  保留静态封面并链接到实际视频。先确认托管限制，再确定编码体积；附件限制和
  H.264 兼容性建议见 [GitHub 附件说明](https://docs.github.com/en/get-started/writing-on-github/working-with-advanced-formatting/attaching-files)。
  托管地址可用不等于实际能播放，替换前检查公开访问和播放；没有可用地址则保留视频待补。
- 本轮不引入 Git LFS，也不新增自动循环动图。旧 GIF/视频保持历史演示用途，
  不迁移或改写 Git 历史；停止新增大体积录屏到仓库。

## 怎样直接替换 README 占位

当前两个 README 的五个位置统一使用 `PA-MEDIA:<ID>:START` 与
`PA-MEDIA:<ID>:END` 注释。可见 HTML 表格明确标注“素材待补 / Media placeholder”，
没有不存在的图片路径或假播放链接。

1. 按上节规则优化真实图片，放到 `docs/assets/readme/`，可采用上表文件名；视频另行托管，不提交进 Git。
2. 搜索相应 ID，将 START/END 注释之间的整块表格替换为图片及必要图注，保留标记
   便于两种语言对应。S1 默认使用主图兼视频封面，并加实际可访问的 V1 视频入口；另选封面时也不重复堆放近似画面。
3. 两个 README 使用相同资源，分别提供描述性 alt 和图注；说明实际版本、平台和
   界面语言。不要只写“截图”，也不要在图注贴内部运行日志。
4. 视频由用户点击播放，保留静态画面。没有视频地址时可先替换已取得的图片，并
   明确视频待补，不填猜测地址或做不可用的播放按钮。采用备用版时按其规则同步说明
   实际覆盖的流程和主动提示缺口，手动结果不标成主动过程。
5. 默认 ID 顺序为 **S1 → S4 → S3 → S7 → S8**。S2/S5/S6 没有预建独立占位，
   按画面价值决定替换/补充，避免开头重复同一幅图。
