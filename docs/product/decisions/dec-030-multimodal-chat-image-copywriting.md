# DEC-030 — 多模态 Chat 与基于图片的个性化文案

Decision ID: DEC-030
Status: Accepted
Updated: 2026-09-06
Authority: B-129 设计讨论中的用户明确选择；2026-09-06 按用户“好的继续”承接上一轮整理 DEC-030 与 Product Spec 的提议。Accepted 仅指下列产品边界，不表示技术方案已验证或获得实施授权。
Work item: B-129

## Context

用户希望把旅行、日常记录或外部图片放进 Chat，自然地理解图片、表达感受，
并在需要时保存图文笔记。个性化来自有来源的相关笔记和适用的表达参考，
不要求用户先管理风格档案，也不把 PA 扩展为独立社交媒体发布工具。

2026-08-11 的初始分析提出图片理解、个性化文案、图片生成三层，并把
“生成即 Capture”“保存满意文案即积累风格”当作冷启动策略。
后续用户明确区分本次文字认可与长期风格认可，本次更新以实际选择替代这些假设。
原有使用场景、低配置负担与 vault 背景价值保留；早期竞品推断、主观评分、
“使用几次即可学会风格”和三层合计工期不再作为当前事实或交付承诺。

与 [North Star](../pa-product-north-star.md) 的连接是：降低记录真实想法的摩擦，
让既有笔记在表达时有用；生成内容仍由用户决定是否进入笔记或成为风格参考。

## Options Considered

| 选择 | 收益与代价 | 本次结论与依据 |
| --- | --- | --- |
| 首版包含三层能力，或先做理解、文案与保存 | 图片生成会扩大 provider、费用、媒体生命周期与交付范围 | 用户选择“图片理解 + 个性化文案 + 保存；图片生成后续推进” |
| 手机发图、电脑继续同一聊天，或各设备分别续聊 | 跨设备聊天还需要历史与引用同步，不能由图片入 vault 自动获得 | 用户选择“首版同一设备续聊即可，手机和电脑分别可用” |
| 独立视觉模型，或沿用当前 Chat 模型 | 单独模型增加配置；沿用时必须说明模型不兼容并保留草稿 | 用户选择“沿用当前 Chat 模型，不支持时引导用户切换” |
| 仅存压缩图，或原图与副本分开 | 原图便于以后复用，但增加空间与同步负担 | 用户要求“聊天里可以显示处理后的副本，但是原图要能追踪到后续可能复用” |
| 生成自动保存，或显式保存 | 自动保存会把未认可的草稿变成长期笔记 | 用户选择“用户点‘保存为笔记’后进入 vault，并区分 AI 草稿与用户修改稿” |
| 保存同时学习风格，或独立风格动作 | 保存不能证明用户希望未来沿用这次表达 | 用户明确“保存笔记只是认可这次生成的文字不代表风格” |
| 全部写作默认沿用，或仅类似场景参考 | 全局偏好容易让旅行文案影响工作邮件等其他写作 | 用户在明确选项中选择“类似场景的文案” |

## Decision

### 已确认的产品边界

1. **首版范围**：在现有 Chat 中支持用户主动添加图片、图片理解、个性化文案和
   显式图文保存。手机与桌面分别可用，支持同设备续聊；图片生成与跨设备聊天后续推进。
   2026-09-06 用户明确选择首版优先完整处理静态图片：动画 GIF/APNG/WebP 与
   依赖外部资源的 SVG 保留原件并提示提供静态 PNG/JPEG，不静默取首帧、不联网
   补齐外部资源；静态且可独立渲染的 SVG 继续走本地转换。完整动画理解与外部
   资源 SVG 渲染留到后续，不作为本次交付条件。
2. **模型**：沿用当前 Chat 模型。已知不支持图片时在添加/发送处解释并引导切换；
   未知能力保留实际尝试和失败恢复路径，不能仅凭 provider 名称判定。已有文字与
   图片草稿不能因切模型或请求失败丢失，不得静默改成无图请求。
3. **原图**：外部图片通过聊天主动加入，原图保存在 Obsidian 附件目录的 PA 子目录
   （例如 pa-images）。聊天可显示处理副本，原图可定位并供后续复用；已有 vault
   图片可引用原文件。不能把“系统可能先转码”当作降低原图要求的默认许可。
4. **同步**：原图子目录默认以排除 Obsidian Sync、Git 与 iCloud 同步为目标。
   可可靠自动完成的部分自动处理；无法自动完成时，按用户接受的方式在首次使用
   通知和文档中指导手动操作。不能把 PA 自己的内容排除设置当作三类同步排除，
   也不能把关闭通知或已给出指南显示为“已验证排除”。手动排除前无法确认是否
   已上传时，提示可能同步并继续导入，不要求先完成配置或证明未上传。
5. **发送与存储生命周期**：只处理用户主动加入的图片；模型接收去除源敏感元数据的
   处理副本，原图保持不变。可重建副本使用有容量上限的本设备缓存；删除聊天或
   清缓存不自动删原图，原图清理需用户动作和可用的引用/空间说明。
   2026-09-06 用户明确接受 iOS 的删除入口调整：PA 列出并打开原图，由用户
   在 Obsidian 中手动删除；Desktop 继续由 PA 核对后移入回收站，两端均可
   清处理缓存。原因是 iOS 公共 API 不提供排除符号链接/越界所需的路径证明；
   不引入私有文件接口。后续公共能力可验证时，再评估恢复 PA 内直接删除。
6. **保存**：“保存为笔记”默认带上该文案版本的全部关联图片，不区分参考图与
   目标主题图，不按用途自动筛除；只有用户明确调整才改变集合。复用 Obsidian
   的目标笔记附件规则。正式笔记图片附件从原图取得，并按正常附件规则参与同步；
   2026-09-06 用户明确确认 HEIC 的窄例外：正式保存 JPEG，HEIC 原件继续留在
   pa-images，保存可追溯的来源关联，不额外复制一份正式 HEIC 附件。已有 vault
   原图仍留在既有位置。其他设备可能仅有 JPEG；原图目录排除成功时，不能
   承诺那些设备也能取得 HEIC。其他格式沿原附件规则。保存固定用户选中的文字
   版本，区分 AI 原稿与用户修改稿。
7. **风格**：保存、局部改写或“这次短一点”不构成长期风格授权。
   “以后参考这种风格”是独立动作，仅作用于类似场景的文案，保留获确认的版本与
   来源并可取消；当次要求优先。自动画像提取和最终持久化也需遵守该边界。
8. **Memory**：不自动对整个图库或原图目录进行视觉索引；同一聊天可追问关联图片，
   保存的笔记文字按现有资格与数据边界参与 Memory。相关背景不能冒充本次照片的
   人物、地点或经历；没有可用 Memory 时仍可根据图片和当次要求生成文案。

这些选择不扩大既有文件排除、跨 vault、provider 或 Memory 权限。写入控制后续
由 PA 能力演进承接，不把现有 Operations 开关固化为 B-129 的新增产品门禁。
具体用户流程、REQ/AC 和兼容细化见 [Product Spec](../specs/pa-multimodal-chat-product-spec.md)。
Product Spec 保留当前产品契约；技术实现见 Architecture。本记录不把后续建议
或验收范围之外的能力一并标为用户批准。

### 2026-09-06 评审处置

用户对独立评审的三项意见明确裁定：

- 图片都需要保留，不区分参考或目标主题；不采纳“默认仅保存主体图片”的建议。
- 手动排除前无法确认是否上传，沿用既有提示与指南；不增加等待配置或验证未上传的门禁。
- 写入权限控制后续将随 PA 能力调整取消，当前方案不算绕过；撤下针对现有开关
  的新增验收建议。该处置不表示本轮已取消运行时权限，不改变用户显式保存的要求。

### 2026-09-06 生产验证后的兼容补充

用户逐项明确选择“补安全升级并验证”和“兼容单个完整 JSON 代码块”：

- 旧设备停在 Memory legacy/compatibility 时，新增用户主动触发的“检查并升级”
  入口。完整核对旧资料、真实来源和撤销状态后才原子切换，失败保持旧模式并
  说明原因。不清库、不略过缺证据记录、不发送资料给 AI、不重建 Memory，
  不自动开启提取。升级后恢复须遵守既有恢复证据与期限，不能复活已忘记内容。
  这替代首版仅提示旧设备不能使用风格参考的限制；不承诺所有旧资料都可升级。
- 原协议仅接受裸 JSON；真实模型三次以完整 JSON 代码块返回，现批准兼容
  整个最终回复只有一个完整、标注 `json` 的三反引号代码块（标记大小写不敏感，
  开闭标记独占一行，允许外层空白与 LF/CRLF）。仍核对原始长度预算、严格
  schema、本次 requestId 和正常完成证据，不从混杂文本猜正文；多块、其他
  标记、尾随说明、格式错误或中断仍走人工恢复。不增加模型调用。若兼容失效，
  可回到原裸 JSON 解析分支及人工恢复，已保存正文与版本不受影响。

上述是新增的明确批准边界；实现和验收状态只见 Tracker。

### 替代早期假设

- “生成即 Capture”改为用户显式保存；聊天历史持久化与创建 vault 笔记是两件事。
- “保存满意文案即学习风格”改为独立、可撤销且限于类似场景的风格参考。
- “先有足够个人数据才能使用”改为无 Memory 时也可完成基本图文创作。
- “原图入 vault 即支持跨设备续聊”不成立；首版只承诺各设备分别使用和同设备续聊。
- 图片生成的商业化与收费方式不在本次决定范围内。

## Consequences

### 产品与数据

- 用户可以忽略未保存的生成结果，不产生自动笔记或风格管理任务。
- 原图、副本缓存和正式笔记附件可能各占一份空间，需分别说明用途与清理后果；
  不以压缩、去重或同步设置为名自动删除原图、修改已跟踪 Git 文件或清除云端数据。
- 正式附件的正常同步与原图目录的排除目标同时存在，保存预览应说明这一差别。
- 风格参考不得借用整 vault / 全部未来回答的默认范围绕过“类似场景”约束。
- 文案正文与参考材料分离；材料记录只证明向本次回答提供了哪些背景，不证明模型
  逐项采纳或逐句引用。复制和保存不得靠重新生成或事后正则剥离来保持正文版本。

### 当前技术承接

设计时的文字 Chat 基线已由类型化图片引用、最终请求边界的副本读取及 B-128
上下文接线承接。图文保存使用固定版本与持久 SaveReceipt，执行和重试不再次
调用 Agent；聊天提取、候选准入和生成笔记均区分 host 来源，显式风格单独治理。
稳定接口、存储生命周期与恢复规则见
[Multimodal Chat Architecture](../../architecture/multimodal-chat-architecture.md)。
这里不将实现存在等同于全部实机 UI 或任意 provider 效果通过。

### 兼容决定与工程验证边界

2026-09-06 P0 实测补充：Obsidian 公共附件 API 只把实际存在的 note 作为
相对目录锚点；新 note 路径尚不存在时会回到 vault 根路径。用户据此明确同意
保存顺序改为“先登记保存记录并创建选定正文，再补齐全部图片和嵌入链接”。
中断时保留可查看、标为未完成的笔记，重试先核对已写内容，不能覆盖用户编辑。
此保存顺序调整不增加生成调用，也不改变默认保存全部关联图片；后续 HEIC
正式 JPEG 的同步例外由上方独立保存决定承接。
具体步骤见 [固定保存与失败恢复](../../architecture/multimodal-chat-architecture.md#固定保存与失败恢复)。

1. **格式与真实原图获取**：JPEG/PNG/WebP、HEIC/HEIF、GIF/APNG/WebP、SVG
   的原件保留、预览、模型发送是不同能力。动画与外部资源 SVG 按上述明确决定
   保留并提示提供静态图；其他未经验证的格式不因本次决定被自动排除或声称支持。
   系统相册可能先转换文件，需验证能否取得应保留的原文件；不能悄悄降格原图承诺。
   **2026-09-06 复测后的明确决定：**用户选择“采用系统转换，失败时提示提供
   JPEG”。不内置 libheif；优先利用设备已有解码能力生成 JPEG，macOS 原生
   解码失败后可调用固定系统转换器。不可转换的平台或失败输入保留已经取得的
   原图和当前草稿，提示提供 JPEG；不承诺所有设备均能自动处理 HEIC，不上传
   远程转码、不自动安装解码器、不改发原图。此决定替代此前 libheif 接入选择，
   不改变其他格式的待验证边界，也不把新添加的 JPEG 冒充原 HEIC 的原件。
   P0 当时两端笔记均显示 HEIC 文件卡；本地转换可行性和后续生产保存/重载证据
   分别保留于 [限定验证](../../archive/2026/b129-multimodal-chat-validation.md)。
   正式 HEIC/JPEG 关系沿上方决定；原 libheif 候选从未加入正式 package/lock，
   早期研究由 Git 历史保留，不作为当前依赖或支持承诺。
2. **同步**：当前不采用 iCloud .nosync 或原生属性作为可靠的插件级排除方案。
   自动排除、各设备设置、已上传/已跟踪内容与原图保留分别核实，未知状态不冒充完成。
3. **目录锚点**：附件规则可以相对笔记；无关联笔记的固定根层逻辑锚点、真实
   TFile 的相对目录及设置变化后的引用/提示由当前 Architecture 承接；两端生产
   验证与目录规则证据分别记录，不从目录解析推导同步排除。
4. **资源与画质**：单图像素/字节、批量数量、照片质量、截图小字清晰度、请求预算
   和缓存容量经 P0 有界实验校准，当前数值以源码 IMAGE_POLICY 为准。单图阶梯
   不等于所有输入和设备的保证；实测要求超出产品边界时再由用户决定。

公开证据：

- [Obsidian 附件规则](https://obsidian.md/help/attachments) 与
  [官方 API 声明](https://github.com/obsidianmd/obsidian-api/blob/master/obsidian.d.ts)
  支持复用附件路径和链接能力，不证明跨文件事务。
- [Obsidian Sync 排除设置](https://obsidian.md/help/sync/settings) 与
  [Git ignore 规则](https://git-scm.com/docs/gitignore) 各有独立边界；ignore 不使已跟踪文件自动退出跟踪。
- [Apple 归档 iCloud 指南](https://developer.apple.com/library/archive/documentation/General/Conceptual/iCloudDesignGuide/Chapters/iCloudFundametals.html)
  记载 .nosync，也说明父目录移除/驱逐可能删除其中内容；
  [当前原生排除属性](https://developer.apple.com/documentation/foundation/urlresourcevalues/ubiquitousitemisexcludedfromsync)
  不证明 Obsidian 插件可在所有目标平台使用。排除同步不是原图保留保证。
- [WebKit Safari 17 的 HEIC 支持](https://webkit.org/blog/14445/webkit-features-in-safari-17-0/)
  不能外推为 Obsidian Desktop 支持；
  [选图转换记录](https://bugs.webkit.org/show_bug.cgi?id=303803) 说明导入路径仍需实测。
- [Canvas toBlob](https://developer.mozilla.org/en-US/docs/Web/API/HTMLCanvasElement/toBlob)
  可用于像素重建后的编码，但仍需验证方向、实际输出类型与敏感元数据清除；
  不承诺“文件中完全没有任何元数据”。

## Revisit Trigger

- 目标手机/桌面无法可靠取得、保留或再次读取原图，需要改变导入或存储方案。
- 有实测证据要求缩窄格式、限制多图能力、引入转换库或更换模型/provider 架构。
- 同步方案会造成原图丢失、意外上传或不可承受的附件体积。
- 自动提取或场景选择无法阻止本次表达污染长期风格，或取消后仍继续生效。
- 用户明确要求图片生成、跨设备聊天/风格同步或图库检索，再单独评估范围与成本。

这些条件触发的是带证据的取舍讨论；不允许先缩窄已确认边界再补写批准。
