# DEC-069 — Chat Markdown 表格显示兼容

Decision ID: DEC-069
Status: Accepted
Updated: 2026-10-18
Authority: Owner 在本会话确认当前表格修复路线，要求分析三处性能成本并给出方案，随后要求按规范完成设计文档；2026-10-18 授权按 B-179 完成全部开发测试并避免过度设计/测试，独立审查后明确确认收尾 B-179 及提交本地 master。性能候选、推送和发布未授权。
Work item: B-179

## Context

Anthelion 的 Chat 回复中，普通段落紧接完整表头和分隔行，原生渲染结果仍为带竖线的
段落。相同输入只在表头前增加一个空行，就能生成表格。markdown-it 可以识别原输入的
表格结构，因此结论是当前解析规则之间的兼容差异，不能归结为模型输出一定不合法，
也不能推导所有表格都必须有前置空行。

Owner 希望兼顾显示效果和性能，并明确本次集中处理表格，不展开通用增量解析。
test vault 原型验证显示兼容及成本分段后，正式接线与桌面/mobile 交互已完成验收。
原型和最终实现的证据分别记录，不以原型替代完整 Chat 验证。

## Options Considered

| Option | 收益 | 代价 / 结论 |
| --- | --- | --- |
| 只要求模型补空行 | 修改少 | 历史消息和其他模型输出仍可能出现同类边界；不能独立解决显示兼容 |
| 按字符串或正则直接改写所有疑似表格 | 简单 | 可能修改代码、HTML 或普通竖线文本；不采用 |
| 结构识别后只调整显示输入，继续原生渲染 | 复用现有依赖、样式、链接及原生后处理，保留原文 | 选用；首期仅处理顶层普通段落紧接表格的已证实边界 |
| 更换 Chat renderer 或引入通用增量解析框架 | 可以重做整条解析链 | 兼容和生命周期范围明显扩大，当前问题没有此需要；不采用 |

## Decision

1. 复用现有 markdown-it 依赖进行块结构识别；仅当顶层普通段落与有效表格紧邻时，
   在显示副本的表头前插入一个空行。代码、原始 HTML 块、引用/列表中的表格及其他
   非目标内容继续原样交给原生 renderer，不按本次兼容规则改写。
2. 保留 Obsidian `MarkdownRenderer` 和 Chat 现有 owner、Mermaid、链接、滚动及流式
   调度。实时正文、完成正文和历史重开使用同一兼容入口，Mermaid 失败回退保持一致。
3. 消息原文仍是复制、历史、后续上下文和其他原文操作的数据来源；不重写笔记或会话，
   不增加 provider 调用、持久缓存、设置或用户确认。
4. 性能分析区分全文原生构建、DOM 发布后样式/布局，以及现有流式调度。前两项是同一
   渲染链的两段成本；32ms 冷却目前没有已确认缺陷，继续保留。
5. 保留稳定表格 DOM 是后续性能优化的优先候选，尚未授权实施；固定列宽在当前样本中
   没有收益，不作为本次方案。减少原生全文构建需要另行验证，不能用 DOM 复用收益替代。

## Consequences

- 首期恢复已证实的表格显示兼容，避免为一处边界更换整个渲染体系。
- 顶层限定是本次修改边界；原生原有内容能力保持，不承诺本次同时修复引用/列表内的相似症状。
- 原文不变，无数据迁移；回退只撤销显示兼容入口及其 helper，不恢复或覆盖任何用户文件。
- 性能候选必须先证明末行更新、回退、原生后处理和 owner 清理正确，再考虑进入独立实施范围。

## Revisit Trigger

出现新的、可复现的非顶层边界问题，兼容处理本身成为主要成本，或真实 Chat 大表格仍有
可感知卡顿时，沿对应证据重新评估；不因原型收益自动扩大到通用增量解析或全站 DOM 复用。
